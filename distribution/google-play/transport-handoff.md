# Secure transport implementation and remaining release gates

Implemented for candidate 1.0.0 (11). Candidate 10 remains transport-blocked and must not be uploaded. The new source and test results do not replace the required real Android/Windows migration test or a 16KB Android runtime test.

## Connection and trust

The companion defaults to HTTP on **127.0.0.1:4787** for its same-machine configurator and **HTTPS on all interfaces:4788** for paired devices. Explicit Kestrel/environment URL settings are preserved, but non-loopback HTTP configurations fail startup with an actionable error. Request middleware also rejects remote HTTP, loopback HTTP with a non-loopback Host, cross-origin browser requests, cross-site fetches and Forwarded/X-Forwarded-* headers before static files or authentication. Do not put a reverse proxy in front of local administration.

Each installation creates an RSA-3072/SHA-256 TLS certificate, stored persistently in `transport-certificate.secret`. Windows protects the PFX with CurrentUser DPAPI through SecretFile; Schannel uses a user-scoped key handle (an ephemeral-key import does not support its TLS credential acquisition). macOS/Linux use an owner-only file, created with mode 600 before writing. Unix file protection is not encryption. An unreadable certificate fails closed; it is never silently replaced. The certificate is valid for ten years. Explicit replacement/expiry needs a fresh physically verified pairing on every device. No root certificate is installed and no global trust policy is changed.

The physical PC pairing window and authenticated **loopback-only** `/api/pairing/qr` generate a version-2 `deckos://pair` code containing an explicit HTTPS endpoint, SHA-256 fingerprint of the DER leaf certificate, and a cryptographically random 256-bit token. The token expires after three minutes and can be exchanged once. The in-memory token table is bounded. Token expiry uses injected TimeProvider in tests. Tokens never appear in discovery or persist to disk. Keep QR codes, copied codes and clipboard contents private.

The native client completes TLS and checks the actual peer certificate fingerprint **before returning the socket to HttpClient**, so authentication cannot precede pin validation. The post-handshake comparison runs even for CA-valid certificates; a matching badCertificateCallback alone would be insufficient. It accepts an otherwise-untrusted certificate only when the physical-code fingerprint matches, and separately rejects expired/not-yet-valid certificates. This is certificate pinning, not a custom cryptographic protocol. The pin is bound to an immutable PC endpoint/client pool, with only that PC's explicitly forwarded TLS loopback route permitted. Discovery is untrusted metadata and cannot change endpoints or pins.

Manual entry accepts the complete code copied from the PC. An explicitly configured system-CA HTTPS endpoint with a `#token=` fragment also works without a pin, using normal CA and hostname validation. Configure that endpoint's real certificate in Kestrel and obtain its token on the physical PC; do not use a self-signed certificate through this CA-only flow. Custom Kestrel certificates override defaults; the built-in QR fingerprint is for the persistent DeckOS certificate, so a custom-certificate deployment should use its CA-valid manual endpoint. There is no trust-all callback, process-wide HttpOverrides, HTTP fallback, automatic pin rotation or cloud relay.

## Credentials and migration

A successful exchange creates a unique random 256-bit device credential. The companion persists only its SHA-256 hash, device ID, label and creation time in a protected file. The same-PC configurator has **Paired devices**, **Copy secure pairing code** and **Revoke device** controls. Revocation rejects subsequent REST/negotiate requests and aborts existing SignalR connections immediately. The previous global API key works only for the loopback HTTP configurator, never as a LAN device credential.

SavedPc preserves existing IDs, names, preferences and per-PC deck caches. Legacy HTTP records are retained and marked **Re-pair securely**. Their old credentials are moved into the platform secure store without sending them to the old HTTP endpoint. Android uses FlutterSecureStorage with encrypted preferences and a Keystore-protected key; iOS uses Keychain, macOS uses Keychain, Windows uses the plugin's protected storage and Linux uses libsecret. There is no plaintext fallback. Writes complete before plaintext keys are removed. The credential's endpoint and fingerprint binding is stored inside the vault; editing the public preference metadata cannot reuse it with another certificate/endpoint. Store operations are serialized to avoid migration/save races. Vault failure keeps original data and reports that secure storage is unavailable. Android backup/device transfer remain excluded.

Physical re-pairing replaces connection fields for a legacy PC at the same host while preserving its existing ID and caches. No profile, integration account, tile/grid/shape setting or provider secret is reset. Forgetting a phone connection is separate from revoking its credential on the PC.

## All network paths

Dio REST, icons, images, binary upload/download and SignalR negotiation share the endpoint policy. A narrow ITransport adapter supplies a verified HttpClient to native WebSocket.connect, including reconnects. Native credentials use headers, never URL query strings. Cached absolute URLs to another endpoint are rejected before authentication. Switching PCs closes the old HTTP pool, stops old SignalR identity/retries and guards delayed route selection by generation.

Legacy ADB reverses to HTTP cannot acquire local privileges: forwarding-process detection uses the actual local listener port, including old port 4787. USB forwards TLS to the same PC certificate on phone loopback port 4788; it does not access the loopback HTTP administrator listener. A lost route can move only to the saved PC's pinned HTTPS endpoint. GET may retry after rerouting; actions/uploads are not replayed automatically because they may already have reached the PC. Android release denies cleartext traffic without a loopback exception. The desktop configurator is a separate browser client, served from the same PC, so it does not require Android cleartext access.

Browsers cannot implement native certificate pinning or choose a custom TLS verifier. Remote browser use therefore needs a certificate trusted normally by the browser; do not bypass a browser warning or install a global root merely to pair. The browser QR puts the one-use token in a URL fragment, exchanges it over HTTPS, removes the fragment and keeps the resulting browser credential in that origin's browser storage. Browser WebSocket APIs require credential query transport; only the hub endpoint accepts it, with hosting request-URL logging suppressed. Native devices use headers. The same-machine configurator continues to work on loopback HTTP.

## Evidence and limits

Meaningful tests use actual TLS sockets and an isolated real Kestrel companion, not mocks alone. They cover wrong/changed/expired certificates, CA-valid wrong pin on REST and WebSocket with zero observed authenticated requests, CA-only normal validation, large images/uploads, SignalR negotiate/upgrade/reconnect, legacy HTTP with zero requests, PC-switch endpoint guards, malformed/legacy/replayed QR data, vault migration/binding/concurrency, token expiry/replay/concurrent replay, device revocation including an existing hub, local Host/origin/proxy rejection and forbidden remote HTTP configuration. Test certificates are temporary and never installed in the OS trust store. They are not bundled into the app. CI installs .NET for the Flutter TLS fixture generator.

Source checks and loopback tests do not prove the real phone's Android Keystore integration, Windows firewall reachability, physical QR onboarding, USB forwarding, or 16KB runtime behavior. The running old companion must be manually updated only after the staged native files are ready; automatic native-update scripting was previously rejected by policy. Do not work around that restriction. Then install the matching debug APK over the existing debug app (same signature; never uninstall or clear data), scan one new physical PC code and exercise the real flows. The upload-signed AAB is separate and must not replace the debug install. Candidate 11 stays NOT-FOR-UPLOAD until those gates and reviewer access are complete.
